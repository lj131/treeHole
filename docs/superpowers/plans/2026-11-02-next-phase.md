## 二、我在实测里撞到、但还没排期的问题

### P1 她的记忆**没有时间轴**（影响最大，今天实测撞到）

**证据**：10-31 的 E2E 里，用户说「今天有点累，刚下课」，她回：

> （嗯了一声）那就别硬撑着聊。（停顿一下）**明天三点半**，撑得住就来，撑不住也别勉强。

而"明天三点半"来自 **9 天前**的一条长期记忆（"……三人约好明天下午三点集合"）。

**原因（已查证）**：
- `long_memory` 在 `.rag.json` 里是 `list[str]`，**没有任何时间戳**
- `prompt.build_memory_summary()` 把记忆原样注入，RAG 检索回来的也没有日期
- 模型拿到"明天下午三点集合"这句话，无法知道它是 9 天前说的

**为什么这条排第一**：陪伴类产品里，"她记错时间"比"少一个功能"更伤。
用户不会因为少一个导出按钮出戏，但会因为"她把我上周的约定当成明天"出戏。

### P2 群聊插嘴是**均匀随机**，不看任何上下文

`group_chat.pick_heckler()` 从候选里 `hash % len(pool)` 取一个。
不看关系强度、不看性格、不看谁刚说过话、不看这轮内容跟谁相关。

**已记录的观察**：4 条消息里 2 条有人插嘴（50%），体感偏吵。
（样本很小，n=4，只能当方向不能当结论 —— 这正是埋点要解决的。）

### P3 多角色导出缺失

`GET /export` 只导**当前角色**。重度用户有多个角色，"全账号纪念册"是真实需求。

### P4 调参被数据阻塞

埋点有了，但没有真实使用数据。**这一项不该现在做**，做了就是继续拍脑袋。

### 批次 1：给长期记忆装一条时间轴

**目标**：让她知道"这是哪天的事"，不再把上周的约定说成明天。

**做法（零 schema 迁移优先）**

1. **写入侧统一加日期前缀**：`MemoryCenter.add_long_memory()` 里把
   `"我们约好..."` 写成 `"（10月30日）我们约好..."`。
   **只有这一个入口** —— 已查证全部 6 处写入（记忆提取 / 活动结算 / 手动新增 /
   会话管理 / NPC 互动）都走它，改一处即可全覆盖。
2. **读取侧在 prompt 里解释这个前缀**：`build_memory_summary()` 加一句
   "带日期的记忆按日期理解；**没带日期的记忆时间不明，不要当成最近发生的事**"
   —— 这句同时兜住历史数据（旧记忆没有前缀，不迁移）。
3. **匹配逻辑要前缀无关**：`update_long_memory()` / `delete_long_memory()` 是按
   **文本完全相等**匹配的。加了前缀后，LLM 返回的 `old_memory` 不会精确复现
   "（10月30日）"，更新会**静默失败**。
   所以这两个方法要先把前缀剥掉再比较；更新时**沿用原来的日期**（改的是内容，不是时间）。

**为什么不改 schema（`list[str]` → `list[{text, at}]`）**：
那是真源结构变更，要同步迁移 `.rag.json`、`_index_to_rag`、导出、记忆编辑页、测试。
收益一样，风险大一个数量级。**先把前缀方案跑一段时间，真需要结构化再迁。**

**验收**
- 单测：写入带日期；**同文本去重仍生效**（不能因为日期不同而重复存）；
  `update`/`delete` 对带前缀的旧数据仍然命中；旧数据（无前缀）渲染不报错
- 实测：注入一条 9 天前的"明天三点半"记忆 → 今天聊"好累" → 她**不该**再说"明天"
- 回归：记忆编辑页（MemoryView）能正常显示/编辑带前缀的条目

**风险**
- 记忆文本被改 → 导出和 UI 会显示前缀（可接受，甚至是改进：用户能看到她什么时候记住的）
- 如果 LLM 自己也在文本里写"明天"，前缀解决不了**文本内部**的相对时间 ——
  这需要 prompt 里额外要求"记忆里写绝对时间"，可放进同一次改动

### 批次 2：群聊发言权调度

**目标**：从"随机抽一个人插嘴"变成"该说话的人说话"。

**做法**（`group_chat.plan_group()` 改成加权调度，仍是**纯函数**，可测）

- **硬门（排除）**：不在场 / 按 `circadian` 正在睡 → 直接排除
- **权重**：
  | 信号 | 来源 | 方向 |
  |---|---|---|
  | 内容相关 | 本轮 RAG 检索命中了谁的集合（`u{uid}_{char}_*` 解析出 char_id） | 命中 → 加权 |
  | 关系强度 | `memory.favorability` / `tension` | 越高越可能接话 |
  | 性格外向 | 角色 `personality` 关键词 | 外向 → 加权 |
  | 公平 | 最近 N 轮插过嘴的人 | 降权（防连庄） |
- **概率**：保留 25% 的基础概率，但"这一轮已经有人接过话"时降为 0

**验收**
- 单测：主角永不被选；同轮不重复；权重排序可验证（给定输入 → 确定输出）；
  连庄被压制；候选全被硬门排除时返回空
- 实测：连聊 5 轮，看插嘴的人是否合理（不连庄、不总是最不熟的那个）

**风险**：容易做成"每人轮流说一句"的假群聊。**判据**：连续两轮出现同一个人插嘴，
或插嘴者与话题无关，都算失败。

### 批次 3：多角色导出

**目标**：一次导出**账号下所有角色**的纪念册。

**做法**
- `GET /export?scope=all`（默认仍是当前角色，不改现有行为）
- 循环 `collect_export_data()` 合并：markdown 每个角色一章；
  json 变成 `{"characters": [...]}`
- 文件名带角色数；**每个角色的数据严格隔离**（A 的记忆不能出现在 B 章）

**验收**
- 单测：合并结构正确；**跨角色不串数据**（这条必须有，是这类功能唯一的真风险）
- 实测：两个角色各导一次 + 合并导一次，对比内容一致
