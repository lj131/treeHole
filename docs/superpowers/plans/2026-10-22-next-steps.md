## 二、🔴 我发现的真问题（按严重度排序）

### P0 — 后台 tick 验证盲区 ✅ **已补（2026-10-22）**

**证据**（已查证，`funcation/world_tick_scheduler.py:273`）：
`RUN_BACKGROUND_TICK` **默认是 `"1"`（开启）**，只有显式设成 `"0"` 才禁用。
而本地环境被设成了 0（启动日志明确打出），真实数据 `dreams: []`、
`dream: null`（`_record_dream` 从未执行）。

**修正我最初的判断**：我一开始以为"生产环境可能也没开、那 E1 日报/梦境/世界演化
全是死的"—— **这个推断是错的**。生产默认开启，受影响的只是**本地/CI**。

**真实性质是"验证盲区"而非"功能失效"**：
世界演化、梦境生成、世界日报的事件积累、NPC 自主互动全都挂在 tick 上，
而**我在本地从未能让 tick 跑起来一次**。也就是说：
这几天我说"E1 日报做完了""梦境引擎完整"，但** tick 链路本身我一次都没验证过** ——
E9 日记是靠"懒生成"绕开 tick 才看到效果的。

**要做的**：
1. 本地用 `RUN_BACKGROUND_TICK=1` 起一次，把 tick 链路（世界演化 → 梦境 → 日报 →
   NPC 互动）**完整跑一遍**，确认它真的工作（这是补盲，不是加功能）
2. 给 tick 加可观测点（`GET /health` 里加"上次 tick 时间/成功失败"，
   和 RAG 的 `quarantine_count` 一个思路 —— 静默失效是最贵的）
3. 若 tick 在生产环境有稳定性问题（LLM 失败、并发写），评估是否把关键路径
   改成"懒生成兜底"（像 E9 那样）：**tick 跑就更好，不跑也不零****

**验证结论（本地实测，`RUN_BACKGROUND_TICK=1`）**：

| 子链路 | 结果 | 证据 |
|---|---|---|
| 世界演化 | ✅ 通过 | 事件进度推进：体育馆漏水 40%→60%、校庆风波 0%→20%；`meta.updated_at` / `last_bg_tick_time` 更新 |
| NPC 互动 | ✅ 通过 | 日志 `[interaction] 冲突已通知：linwan（和 maid，severity=2）` |
| 梦境生成 | ✅ 通过 | 有素材时生成；**没素材时不编**（`chat_summary` 为空 → 不生成，这是正确门控） |
| 门控 | ✅ 正确 | 三项都有 due 判断，不会空转烧 LLM |

**梦境实测内容**（素材是"海报/五百块预算/展览"）：
> 我梦到那张海报上的字全被风吹散了……五百块的预算在梦里变成一堆硬币，
> 我蹲在地上数，数到一半发现怎么都凑不齐……最后只是伸手帮你把边角按平了。

取材正确、风格荒诞跳跃 —— 和 E9 日记的"平实第一人称"对比鲜明，
**两个引擎的视角区分是真的生效的**（之前只有设计，没验证过）。

**两个实测发现**：
1. `WORLD_TICK_LOOP_SEC` 有**下限 60 秒**、`WORLD_TICK_MIN_INTERVAL_MIN` 下限 1 分钟
   （低于会被 `system_config` 拒绝并用默认值，日志有 WARNING）。
   想快速验证只能重启服务触发"启动时立即 tick 一次"。
2. `interaction_agent` **不在 tick 里**，只有手动端点 `/world/interaction/simulate`
   （tick 日志里的冲突通知来自别处）—— 设计如此，不是 bug。

**可观测点已加（2026-10-23，`5a31ff3`）**：`GET /health` 新增 `tick` 段，
四种状态（禁用 / 启用未启动 / 运行中 / 异常）都能一眼区分，实测：

| 环境 | `/health` 的 tick.summary |
|---|---|
| `RUN_BACKGROUND_TICK=0`（本地默认） | 已禁用（RUN_BACKGROUND_TICK=0）：世界演化/梦境/NPC 互动都不会自动跑 |
| `=1` 刚起来 | 已启用但还没启动（可能刚起来，等 60s） |
| `=1` 70 秒后 | 运行中（累计 1 轮，最近一轮 tick 1/9 人） |

**"禁用"和"启用但没启动"必须分开** —— 前者是配置问题，后者是刚启动，
责任完全不同。这正是我三天糊里糊涂的直接原因。

**仍剩余**：生产环境的稳定性（LLM 失败/并发写）未验证 —— 本地只跑过一次。

### 第三优先：产品深化（确认前两项之后再动）

按"情感价值 × 技术债"排序：

| 方向 | 为什么 | 注意 |
|---|---|---|
| **活动邀请的"过程"** | E11 约完了就断了（接受后只有 prompt 里一句约定）。加"活动当天她会提起/活动后留下记忆"闭环，情感回报最高 | 别做成任务系统，保持轻 |
| **群聊的发言权调度** | 现在只有"主角 + 1 个插嘴者"。真群聊该有"抢话、接话、沉默" | 计划原文就说这是 E8 的最大缺口；别做成轮播 |
| **梦境真正跑起来** | `dream_agent` 引擎完整但从未执行过（tick 禁用）。接通后**梦境+日记+活动**构成她的"内心世界"三件套 | 依赖 P0 先解决 |
| **多角色导出** | E11 只导当前角色。重度用户有多个角色，"全账号纪念册"有真实需求 | 要处理跨角色合并；别做成 ZIP 打包那种重活 |

### 明确不建议做（记录在案，避免以后反复被提）

- **导入/反向恢复**：导出后想读回来，需要一整套冲突解决逻辑（本地改过的 vs 线上新的），
  投入产出比极低，且容易搞坏数据。
- **事件编辑/删除 UI**：E10 已刻意不做。世界事件是"演化"而非"表格"，
  能改能删会让世界失去重量。
- **给 256 个音色槽做下拉**：255 个选到就是静音（10-14 实测）。
- **启动预热克隆引擎**：会让不使用克隆的用户白占 480MB 内存（10-12 的决定）。
