## 二、🔴 我发现的真问题（按严重度排序）

### P0 — 后台 tick 在本地被禁用，我有一条验证盲区

**证据**（已查证，`funcation/world_tick_scheduler.py:273`）：
`RUN_BACKGROUND_TICK` **默认是 `"1"`（开启）**，只有显式设成 `"0"` 才禁用。
而本地环境被设成了 0（启动日志明确打出），真实数据 `dreams: []`、
`dream: null`（`_record_dream` 从未执行）。

**修正我最初的判断**：我一开始以为"生产环境可能也没开、那 E1 日报/梦境/世界演化
全是死的"—— **这个推断是错的**。生产默认开启，受影响的只是**本地/CI**。

**真实性质是"验证盲区"而非"功能失效"**：
世界演化、梦境生成、世界日报的事件积累、NPC 自主互动全都挂在 tick 上，
而**我在本地从未能让 tick 跑起来一次**。也就是说：
这几天我说"E1 日报做完了""梦境引擎完整"，但** tick 链路本身我一次都没验证过** ——
E9 日记是靠"懒生成"绕开 tick 才看到效果的。

**要做的**：
1. 本地用 `RUN_BACKGROUND_TICK=1` 起一次，把 tick 链路（世界演化 → 梦境 → 日报 →
   NPC 互动）**完整跑一遍**，确认它真的工作（这是补盲，不是加功能）
2. 给 tick 加可观测点（`GET /health` 里加"上次 tick 时间/成功失败"，
   和 RAG 的 `quarantine_count` 一个思路 —— 静默失效是最贵的）
3. 若 tick 在生产环境有稳定性问题（LLM 失败、并发写），评估是否把关键路径
   改成"懒生成兜底"（像 E9 那样）：**tick 跑就更好，不跑也不零****

### P1 — 一批频率/门槛参数只有理论值，没有真实反馈

这几天为了验证功能，我反复调过这些参数，**没有一次是基于真实使用数据**：

| 功能 | 参数 | 我观察到的事实 |
|---|---|---|
| E7 主动来电 | 30%/小时 + 每日 3 次 | 白天 15 小时命中 3 次（正好打满上限）—— **上限是不是太松** |
| E8 群聊插嘴 | 25%/轮 | 实测 4 条消息中 2 条插嘴（50%）—— **体感偏吵** |
| E11 活动邀请 | 25%/轮 + 好感度 ≥30 | 实测 8 条才命中 1 次（叠加门槛后 ≈12%）—— **可能太低，约不出来** |
| E11 拒绝冷却 | 3 天 | 无数据 |
| E9 日记 | 一天一篇 | 懒生成，无频率问题 |

**要做的**：把这些参数提成配置（`system_config` 已有配置体系），
加一个简单的**计数埋点**（触发/接受/拒绝多少次），
跑一段时间后再定值。**不要继续拍脑袋。**

### P1 — 同类安全隐患**已确认存在**（不止 E11 那一处）

E11 的测试抓出了 `character_state` 被"整个 dict 倒出去"的泄漏面。我当时判断
"同类风险点待审"，**现在已查证一个**：

**`GET /memory/full`（`api.py:1888`）直接 `return {"memory": mem}` ——
把整个 memory dict 原样吐给前端**（`require_auth`，普通登录用户即可）。
memory 里有什么就吐什么，没有任何字段过滤。

它和 E11 的区别只是"还没人在里面塞过 secret"，不是"设计上安全"。
`character_state`/`self_awareness`/`proactive` 这些内部状态字段，
以及未来任何新加的字段，都会**自动**出现在响应里。

**其他待审**（同样模式，未逐个确认）：
- `/admin/*` 各端点 —— 管理员接口权限大，更容易带出敏感字段
- 角色卡片/世界状态的"详情"接口 —— 有没有把内部字段
  （`created_by`、内部路径、其他用户 id）一起吐出去

**要做的**：
1. **先修 `/memory/full`**：用 E11 的 `_pick(source, WHITELIST)` 模式收敛字段
   （前端 `MemoryView` 只用得到它显示的那几个，不会破坏界面）
2. 系统审一遍"哪些响应会包含整个 dict"，逐个判断"该不该给前端/该不该给普通用户"
3. 把"**新端点不许返回整个 dict**"写进 `backend/CLAUDE.md` 铁律区

### P2 — 测试的脆弱性（已有两例，说明不是孤例）

1. **E9 时间硬编码**：`TODAY = "2026-10-21"`，跨天后全量跑才红。
   特征是"单跑不红、全量跑红、只在特定日期后出现"—— 极易误判成环境问题。
2. **session 级 mock 漏 mock**（10-14 踩过）：`conftest.disable_rag` 漏一个写函数，
   集成测试就往**真实开发库**写数据。

**要做的**：
- 全局搜测试里的硬编码日期/时间（`2026-`、`datetime(20`），改成相对时间
- 新增"会写向量库/写文件的公开函数"时，强制过一遍 `disable_rag` 的 mock 列表
  （这条建议写进 `backend/CLAUDE.md` 的铁律区）

### P2 — 我自己这三天犯了 4 次判断失误，模式值得记

1. **查错文件就下结论**（E10）：说"`world_event` 没有 events 数组"，
   实际我看的是**世界设定**（`worlds/*.json`），动态事件在 `world_state/*.json`。
2. **造重复轮子**（E10）：写完 `world_event_inject.py` 才发现
   `world_event_agent.create_event()` 已做全部事情。
3. **把"我调错了"当"代码有 bug"**（E10）：`importance` 传字符串拿 422，
   一度判定"schema 与数据不一致"。
4. **改完代码没重启就 E2E**（E11）：看到旧行为以为修复无效。

**共同点**：都在"动手"之前少了**一步交叉验证**（查证要广、结论要可反驳）。
已把教训写进各提交信息，但**流程上值得加一条**：
> 结论和已有实现冲突时，先假设自己查错了，去找第二个证据源。

## 三、后续方向（按我推荐的优先级）

### 第一优先：确认与加固（不做新功能）

1. **P0 tick 验证盲区**（见上）—— 在本地把 tick 链路完整跑一遍，
   它是我唯一没验证过的已上线功能
2. **P1 `/memory/full` 收敛字段**（见上）—— 已确认在吐全量 dict，可直接修
3. **P2 测试脆弱性**（见上）

这三项都不加功能，但每一项都可能改变"我们以为做完了"的判断。

### 第二优先：参数调优 + 可观测（基于数据，不拍脑袋）

- 把 E7/E8/E11 的频率参数提成配置
- 加轻量埋点：触发次数、接受/拒绝、插嘴条数
- 有数据后再定值，并把定值依据写进 `CLAUDE.md`

### 第三优先：产品深化（确认前两项之后再动）

按"情感价值 × 技术债"排序：

| 方向 | 为什么 | 注意 |
|---|---|---|
| **活动邀请的"过程"** | E11 约完了就断了（接受后只有 prompt 里一句约定）。加"活动当天她会提起/活动后留下记忆"闭环，情感回报最高 | 别做成任务系统，保持轻 |
| **群聊的发言权调度** | 现在只有"主角 + 1 个插嘴者"。真群聊该有"抢话、接话、沉默" | 计划原文就说这是 E8 的最大缺口；别做成轮播 |
| **梦境真正跑起来** | `dream_agent` 引擎完整但从未执行过（tick 禁用）。接通后**梦境+日记+活动**构成她的"内心世界"三件套 | 依赖 P0 先解决 |
| **多角色导出** | E11 只导当前角色。重度用户有多个角色，"全账号纪念册"有真实需求 | 要处理跨角色合并；别做成 ZIP 打包那种重活 |

### 明确不建议做（记录在案，避免以后反复被提）

- **导入/反向恢复**：导出后想读回来，需要一整套冲突解决逻辑（本地改过的 vs 线上新的），
  投入产出比极低，且容易搞坏数据。
- **事件编辑/删除 UI**：E10 已刻意不做。世界事件是"演化"而非"表格"，
  能改能删会让世界失去重量。
- **给 256 个音色槽做下拉**：255 个选到就是静音（10-14 实测）。
- **启动预热克隆引擎**：会让不使用克隆的用户白占 480MB 内存（10-12 的决定）。
